CSS Bug
Device-Specific

Welcome offer cannot be dismissed on mobile

A shopper sees the "Take 15% off your first order" offer but cannot dismiss it on a phone.

Reproduction Steps
  1. Open the home page in a narrow viewport (768px wide or less), or use a mobile device.
  2. Refresh the page so the welcome offer and cookie notice are visible.
  3. Tap the × in the lower-right area of the welcome offer.
  4. Observe that the offer remains open.
Comparison Case
  1. Open or resize the same page to a viewport wider than 768px.
  2. Refresh the page.
  3. Click the × in the welcome offer.
  4. Observe that the offer closes normally.
Acceptance Criteria
  1. The welcome offer close (×) control dismisses the offer on viewports 768px and narrower.
  2. The close control has a tap target of at least 44×44px and is not obstructed by the cookie notice or any other overlay.
  3. The cookie notice remains fully visible and functional after the fix.
  4. Behavior on viewports wider than 768px is unchanged.
Your mission: Investigate why the visible close control does not receive mobile taps, identify the underlying layout/layering issue, and propose a fix that preserves the cookie notice and makes the close control easy to tap.

Interaction Bug

Double-clicking Add to Cart creates duplicate cart entries

A shopper clicks the Add to Cart button twice in quick succession and the cart shows duplicate items or a quantity jump that does not match a single purchase.

Reproduction Steps
  1. Open the home or product listing page and locate a product card.
  2. Click or tap the Add to Cart button twice in rapid succession.
  3. Open the cart or cart modal.
  4. Observe that the product appears more than once, or the quantity increases unexpectedly.
Comparison Case
  1. Add the same product once with a single click or tap.
  2. Open the cart.
  3. Observe that the item is added once and the quantity reflects a single purchase.
Acceptance Criteria
  1. Double clicking results in exactly one item added per intended add action.
  2. The button is guarded against double-submission (e.g., disabled while in-flight, debounced, or idempotent).
  3. Normal single-click add-to-cart behavior is preserved, including quantity increments from the cart itself.
  4. No visual regressions or loading states left stuck after the action completes.
Your mission: Investigate why rapid repeated clicks can create duplicate cart entries, identify the unguarded interaction or race condition, and propose a fix that prevents duplicate submissions while preserving normal add-to-cart behavior.

Form Validation Bug

Checkout error message is generic and doesn't indicate which field is wrong

A shopper submits the checkout form and sees a single generic error (e.g., "Please fill in all fields.") without any indication of which field is missing or invalid.

Reproduction Steps
  1. Add any item to the cart and navigate to the checkout page.
  2. Leave one or more required fields blank (for example, leave City or Email empty).
  3. Click Place Order.
  4. Observe the single generic error message with no indication of which field needs attention.
Comparison Case
  1. Fill in every field correctly and submit.
  2. Observe the order is placed successfully with no error message.
Acceptance Criteria
  1. Each invalid or missing field is clearly identified inline (e.g., highlighted with a per-field error message).
  2. The error message names the specific field(s) and explains what is expected.
  3. Valid fields are not flagged as errors.
  4. Successful submission behavior is unchanged.
Your mission: Investigate the checkout form's validation flow, identify where the generic error is produced, and propose a fix that surfaces field-level errors so users know exactly what to correct.

Form Validation Bug

International shoppers cannot complete checkout — postal code rejected

Shoppers selecting a country other than the United States are unable to place an order because their postal code is rejected as invalid.

Reproduction Steps
  1. Add any item to the cart and navigate to the checkout page.
  2. Select a non-US country (for example, Canada, United Kingdom, or Japan).
  3. Fill in all remaining fields, including a valid postal code for that country (e.g., M5V 3A8 for Canada, SW1A 1AA for the UK).
  4. Click Place Order.
  5. Observe that the form rejects the postal code with a US-specific error message.
Comparison Case
  1. Repeat the checkout flow with United States selected and a valid 5-digit ZIP code (e.g., 97201).
  2. Observe that the order submits successfully.
Acceptance Criteria
  1. Postal code validation matches the selected country's format, or accepts any reasonable postal code when the country's format is unknown.
  2. US shoppers continue to have their 5-digit ZIP (with optional +4) validated as before.
  3. Error messaging references the correct country and expected format.
  4. International orders complete successfully end-to-end.
Your mission: Investigate why the postal code check assumes a US format regardless of the selected country, and propose a fix that lets international shoppers complete checkout without regressing US validation.

Form Validation Bug

State/Province selection carries over when the country changes

A shopper changes the selected country in the checkout form, but a previously chosen state or province value silently carries over — so the form submits with a state that doesn't belong to the new country.

Reproduction Steps
  1. Add any item to the cart and navigate to the checkout page.
  2. Select United States as the country and pick a state (e.g., California).
  3. Change the country to a different one (e.g., Germany or United Kingdom).
  4. Fill in the remaining fields and submit — or inspect the form data.
  5. Observe that the state field still holds the previously chosen value ("CA") even though it makes no sense for the new country.
Comparison Case
  1. Reload the page and pick a country only once before submitting.
  2. Observe that the state value corresponds correctly to the selected country.
Acceptance Criteria
  1. Changing the country clears any previously selected state/province value.
  2. The state field re-renders correctly (select vs. free-text input) based on the new country's regions.
  3. The required-field check catches the empty state after a country change instead of allowing a stale value to slip through.
  4. No regressions to the initial country selection flow.
Your mission: Investigate what happens to form.state when the country changes, identify why the stale value is preserved, and propose a fix that resets the state whenever the country selection changes.

Interaction Bug

Add to Cart button on the plant page appears unresponsive with no explanation

A shopper clicks the Add to Cart button on a product card on the plant listing page and nothing happens. There is no message or tooltip explaining why — the item is actually sold out.

Reproduction Steps
  1. Navigate to the plant listing page.
  2. Locate a product card whose item is out of stock.
  3. Click the Add to Cart button on that card.
  4. Observe that nothing happens and no clear message explains why the button is inactive.
Comparison Case
  1. Click Add to Cart on any in-stock product card.
  2. Observe the item is added to the cart and the cart modal opens.
Acceptance Criteria
  1. When an item is out of stock, the button clearly communicates its state (e.g., label changes to "Sold Out", a tooltip appears, or an accessible message is announced).
  2. The out-of-stock status is visible without relying solely on a badge that may be missed.
  3. In-stock behavior is unchanged: click adds the item and opens the cart modal.
  4. The change is accessible to keyboard and screen reader users.
Your mission: Investigate why users perceive the button as broken, identify the missing feedback for the sold-out state, and propose a fix that makes it obvious the item is unavailable while preserving normal add-to-cart behavior.

Data Bug

Broken product image — incorrect image URL

A shopper browsing the store sees a broken or missing image on at least one product card. The image fails to load while the rest of the card renders normally.

Reproduction Steps
  1. Open the plant listing page (or home page).
  2. Scan the product cards for one where the image does not load (broken image icon or empty space).
  3. Open browser DevTools, go to the Network tab, and filter to the failing image request.
  4. Observe a 404 (or other failure) response for that product's image URL.
Comparison Case
  1. Inspect any other product card and confirm its image loads normally.
  2. Compare the failing URL against a working one — the failing product references an incorrect path or filename.
Acceptance Criteria
  1. The affected product's image loads successfully and matches the product.
  2. No 404 (or other failed image) requests remain in the Network tab for product images.
  3. Product cards render consistently with all images visible.
Your mission: Identify the product with the broken image, trace the incorrect URL back to the data source (starter data or migration file), and propose a fix that restores a correct, matching image for that product.

CSS

Cart drawer locks the store — page becomes unresponsive after closing the drawer

After using the cart drawer for a while, the store becomes completely unresponsive. Nothing on the page reacts to clicks — not product cards, not the header nav, nothing. There is no error in the console. Reloading the page fixes it, but it happens again after more shopping.

Reproduction Steps
  1. Add an item to the cart (the drawer opens automatically).
  2. Close the drawer.
  3. Repeat the open/close cycle a few times, using different methods each time (close button, tapping outside the drawer, pressing Escape).
  4. Try to click a product card, the header, or any other control on the page.
  5. Observe that the page silently stops responding to clicks — no error is thrown.
Comparison Case
  1. Open the cart drawer, close it once with the close button, and immediately click a product card.
  2. Observe that the page responds normally.
Acceptance Criteria
  1. The drawer can be opened and closed any number of times, in any combination of ways (button, outside click, Escape), without leaving anything behind that blocks the page.
  2. After the drawer is closed, no element in the DOM captures pointer events over the rest of the page.
  3. Rapid or repeated close actions do not stack overlays or duplicate elements.
  4. Closing the drawer with each method (button, outside click, Escape) produces the same clean end state.
Your mission: Reproduce the lockup reliably, use the DevTools Elements panel to inspect what is left in the DOM after the drawer visually appears gone, and propose a fix that guarantees the drawer and its backdrop are always fully removed on close — regardless of how the user closes it or how many times.

Search Bug

Stale header-search results

As a shopper types in the header search, earlier suggestions can appear after newer ones, so the list does not always match the current query.

Reproduction Steps
  1. Open the app and, in browser DevTools, enable a throttled network profile such as Fast 3G.
  2. In the header search box, quickly type a short query and then extend or replace it — for example type mon and then immediately type monstera.
  3. Repeat with a few different search terms if needed.
  4. Observe that the suggestions may display results for an earlier query instead of the text currently in the input.
Comparison Case
  1. Open the app on a normal network profile or with a stable connection.
  2. Type a new query in the header search box.
  3. Watch the suggestions update as each character is entered.
  4. Observe that the visible suggestions remain consistent with the latest text and do not lag behind the current query.
Acceptance Criteria
  1. Header-search suggestions always correspond to the text currently in the input, regardless of request order or network latency.
  2. Responses from stale (superseded) requests are discarded and never overwrite newer results.
  3. Behavior is verified under a throttled network profile (e.g., Fast 3G) with rapid typing.
  4. No new console errors or unhandled promise rejections introduced by the fix.
Your mission: Investigate why an earlier request can overwrite newer suggestions, identify the race condition, and propose a fix that ensures the visible results always correspond to the latest search text, regardless of request timing.
