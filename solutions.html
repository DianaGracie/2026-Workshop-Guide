1. Welcome offer cannot be dismissed on mobile

← back to bug
Root Cause

On narrow viewports, the cookie notice is stacked above the welcome offer's close (×) button. Because the cookie notice has a higher stacking context (or comes later in DOM order) and a transparent overlay area that overlaps the ×, the tap lands on the cookie notice instead of the button. The button visually appears clickable but never receives the pointer event.

The Fix

Move the close control above any overlapping element and give it a proper tap target. Two changes:

/* welcome-offer.component.scss */
.welcome-offer {
  position: fixed;
  bottom: 1rem; right: 1rem;
  z-index: 10;
  z-index: 1100;   /* above the cookie notice (z-index: 1000) */
}

.welcome-offer .close-btn {
  width: 24px; height: 24px;
  min-width: 44px; min-height: 44px;   /* WCAG 2.5.5 target size */
  display: flex; align-items: center; justify-content: center;
  position: relative; z-index: 1;      /* ensure nothing sits on top */
}
Why This Works
  • Explicit stacking order. Never rely on DOM order for critical overlays — use z-index tokens (e.g., --z-modal, --z-toast) so the layering is intentional and auditable.
  • 44×44 pt tap targets. The WCAG 2.5.5 (AAA) recommendation prevents fat-finger mis-taps on touch devices. A 24px control almost always fails on phones.
  • Test on the smallest common viewport. If the fix works at 320px, it works at 768px too.
Related Pitfalls
  • A parent with overflow: hidden or transform creates a new stacking context and can trap z-index. Check ancestors.
  • Fixed elements with pointer-events: none on a wrapper (used for backdrops) can accidentally cover buttons — always scope pointer events to the visible element only.

2. Double-clicking Add to Cart creates duplicates

← back to bug
Root Cause

The click handler triggers an async add and immediately returns. A rapid second click fires before the first has completed (or before the UI reflects the new state), and the handler runs a second time — appending a duplicate cart entry instead of incrementing an existing one.

The Fix

Guard the button with an in-flight signal so re-entry is impossible during the async add:

// product-card.component.ts
export class ProductCardComponent {
  @Input({ required: true }) product!: Product;
  cart = inject(CartService);
  adding = signal(false);

  addToCart() {
    this.cart.addItem(this.product);
    this.cartModal.open();
  }
  async addToCart() {
    if (this.adding()) return;         // re-entrancy guard
    this.adding.set(true);
    try {
      await this.cart.addItem(this.product);
      this.cartModal.open();
    } finally {
      this.adding.set(false);
    }
  }
}
<!-- product-card.component.html -->
<button
  class="add-btn"
  (click)="addToCart()"
  [disabled]="!product.in_stock">
  [disabled]="!product.in_stock || adding()">
  {{ adding() ? 'Adding…' : 'Add to Cart' }}
</button>
Why This Works
  • Disabling the button prevents the second click at the DOM level — the browser won't dispatch a click on a disabled control.
  • The adding signal is a belt-and-suspenders guard: even if the disabled attribute is bypassed (keyboard, script), the early-return short-circuits re-entry.
  • Better alternative for existing items — make addItem idempotent in the service: if the item already exists, increment quantity; never push a duplicate row. That way the bug can't reappear via other entry points.
Related Pitfalls
  • Do not rely on debounce alone — it delays but doesn't prevent a determined double-submit if the async work is longer than the debounce window.
  • Reset the loading state in a finally block, not in the success path — otherwise a failed add leaves the button permanently disabled.

3. Generic checkout error message

← back to bug
Root Cause

The submit handler in checkout.component.ts checks all required fields in a single boolean expression and, if any are missing, sets one generic error string. Users can't tell which field failed.

src/app/checkout/checkout.component.ts:123–134

The Fix

Collect the specific missing fields, then show a targeted message (and, ideally, per-field inline errors driven by Angular's form state):

// checkout.component.ts
fieldErrors = signal<Record<string, string>>({});

private validate(): boolean {
  const errors: Record<string, string> = {};
  if (!this.form.fullName) errors['fullName'] = 'Full name is required.';
  if (!this.form.email)    errors['email']    = 'Email is required.';
  if (!this.form.address)  errors['address']  = 'Address is required.';
  if (!this.form.country)  errors['country']  = 'Please select a country.';
  if (!this.form.city)     errors['city']     = 'City is required.';
  if (!this.form.state)    errors['state']    = `${this.stateLabel} is required.`;
  if (!this.form.zip)      errors['zip']      = `${this.zipLabel} is required.`;
  this.fieldErrors.set(errors);
  return Object.keys(errors).length === 0;
}

async onSubmit(event: Event) {
  event.preventDefault();
  this.errorMessage.set('');
  if (!this.form.fullName || !this.form.email || /* … */ !this.form.country) {
    this.errorMessage.set('Please fill in all fields.');
    return;
  }
  if (!this.validate()) return;
  // … rest unchanged
}
<!-- checkout.component.html — repeat per field -->
<div class="form-group full" [class.has-error]="fieldErrors()['email']">
  <label for="email">Email</label>
  <input id="email" type="email" [(ngModel)]="form.email" name="email" />
  @if (fieldErrors()['email']) {
    <p class="field-error">{{ fieldErrors()['email'] }}</p>
  }
</div>
Why This Works
  • Field-level errors put the message next to the offending input, cutting the cognitive load to zero.
  • Errors as data (a signal/record) is easier to test than an imperative error string, and it composes cleanly with form-state validators later.
  • Name the field and the expectation — "Email is required" beats "Invalid input"; "Enter a valid Canadian postal code (e.g., M5V 3A8)" beats "Invalid ZIP".
Related Pitfalls
  • Don't clear all errors on every keystroke — only clear a field's error once the user has changed that field.
  • For accessibility, associate error text with the input via aria-describedby and mark the input aria-invalid="true".

4. International postal code rejected

← back to bug
Root Cause

The submit handler always tests the ZIP against US_ZIP_PATTERN, regardless of the selected country. Any valid Canadian, UK, or other international postal code is rejected as "invalid".

src/app/checkout/checkout.component.ts:7, 136–139

The Fix

Look up the appropriate pattern per country, and fall back to a permissive check when the country's format is unknown:

// checkout.component.ts
const US_ZIP_PATTERN = /^\d{5}(-\d{4})?$/;
const POSTAL_PATTERNS: Record<string, { pattern: RegExp; example: string }> = {
  'United States':  { pattern: /^\d{5}(-\d{4})?$/,                  example: '97201' },
  'Canada':         { pattern: /^[A-Za-z]\d[A-Za-z] ?\d[A-Za-z]\d$/, example: 'M5V 3A8' },
  'United Kingdom': { pattern: /^[A-Z]{1,2}\d[A-Z\d]? ?\d[A-Z]{2}$/i, example: 'SW1A 1AA' },
  'Germany':        { pattern: /^\d{5}$/,                            example: '10115' },
  'France':         { pattern: /^\d{5}$/,                            example: '75008' },
  'Japan':          { pattern: /^\d{3}-?\d{4}$/,                     example: '150-0001' },
  'Australia':      { pattern: /^\d{4}$/,                            example: '2000' },
  // …extend as needed. Unknown countries fall through to the permissive check.
};
const FALLBACK_POSTAL = /^[A-Za-z0-9 \-]{3,10}$/;   // any reasonable postal code

// inside onSubmit:
if (!US_ZIP_PATTERN.test(this.form.zip)) {
  this.errorMessage.set('Invalid ZIP code. Please enter a valid 5-digit US ZIP code.');
  return;
}
const rule = POSTAL_PATTERNS[this.form.country];
const pattern = rule?.pattern ?? FALLBACK_POSTAL;
if (!pattern.test(this.form.zip.trim())) {
  const hint = rule ? ` (e.g., ${rule.example})` : '';
  this.errorMessage.set(`Please enter a valid ${this.zipLabel.toLowerCase()} for ${this.form.country}${hint}.`);
  return;
}
Why This Works
  • Country-aware validation is the smallest correct fix — you keep client-side format checking without hard-coding US.
  • A permissive fallback means adding a new country doesn't require a code change on day one — the order still goes through and format can be added later.
  • The error message names the country and shows an example — users understand exactly what format is expected.
Related Pitfalls
  • Regex is a client-side convenience, not authoritative validation. Always re-validate on the server / at order write, and don't reject a real order just because the pattern list is incomplete.
  • Consider libraries like i18n-postal-address or Google's libphonenumber-equivalent for postal codes if the country list grows.

5. State/Province carries over on country change

← back to bug
Root Cause

The onCountryChange handler updates the region list, label, and ZIP label — but never clears form.state. A previous value (e.g., "CA") silently persists and passes the required-field check.

src/app/checkout/checkout.component.ts:109–117 (there's already a // BUG: comment)

The Fix
onCountryChange(): void {
  const country = this.form.country;
  this.form.state = '';                    // reset dependent field
  this.fieldErrors.update(e => ({ ...e, state: '' }));  // clear stale error too
  this.stateOptions = REGIONS[country] ?? [];
  this.hasRegions = this.stateOptions.length > 0;
  this.stateLabel = STATE_LABELS[country] ?? 'State / Province';
  this.zipLabel = country === 'United States' ? 'ZIP Code' : 'Postal Code';
}
Why This Works
  • Dependent fields must be reset when their parent changes. This is a universal form pattern — country → state, category → subcategory, product → variant, and so on.
  • Clearing the error alongside the value avoids showing a stale "State is required" message before the user has even touched the new state input.
  • Prefer reactive forms with updateOn: 'change' and a valueChanges subscription on the country control if you're refactoring — it makes this cascade declarative.
Related Pitfalls
  • Don't reset silently in a way the user can't tell — if the state was already valid, consider preserving it when the new country has the same code (rare, but noticeable if you're switching between US/CA which both have "CA").
  • ZIP validation also depends on country now — clear the ZIP error on country change too.

6. Sold-out Add-to-Cart looks unresponsive

← back to bug
Root Cause

The button is correctly disabled with [disabled]="!product.in_stock", but the only sold-out signal is a small "Out of Stock" badge on the image. On mobile or in quick scans the badge is easy to miss — so users perceive the button as broken.

src/app/product-card/product-card.component.html:24–30

The Fix

Make the button itself carry the message, and expose the state to assistive tech:

<!-- product-card.component.html -->
<button
  class="add-btn"
  (click)="addToCart()"
  [disabled]="!product.in_stock"
  [attr.aria-label]="!product.in_stock
    ? product.name + ' is sold out'
    : 'Add ' + product.name + ' to cart'"
  [title]="!product.in_stock ? 'This item is currently out of stock' : null">
  {{ product.in_stock ? 'Add to Cart' : 'Sold Out' }}
>
  Add to Cart
</button>
/* product-card.component.scss */
.add-btn[disabled] {
  background: var(--surface-alt);
  color: var(--text-muted);
  cursor: not-allowed;
  opacity: 1;   /* the label change is the signal — don't hide it behind opacity */
}
Why This Works
  • The label is the truth. A button that reads "Sold Out" cannot be misinterpreted — no badge required.
  • Cursor and color reinforce disabled state without dimming the label to unreadable.
  • aria-label + title covers screen-reader and hover-tooltip users.
Related Pitfalls
  • Don't remove the "Out of Stock" image badge — it's still useful at a glance across a grid of many cards.
  • If you offer restock notifications, the label becomes an actionable "Notify Me" and the button re-enables — plan for that state.

7. Broken product image URL

← back to bug
Root Cause

One product's image_url in the starter data references a non-existent Pexels asset (typo, deleted photo, or wrong slug mapping). The image tag renders but the network request 404s.

supabase/migrations/20260626145013_sync_product_image_urls.sql

The Fix

Two-part: patch the bad URL and harden the UI against future breakage.

1. Patch the data. Add a new migration (never edit an old one that's been run):

-- supabase/migrations/YYYYMMDDHHMMSS_fix_broken_image.sql
UPDATE products
SET image_url = 'https://images.pexels.com/photos/<correct-id>/pexels-photo-<correct-id>.jpeg?auto=compress&cs=tinysrgb&w=800'
WHERE slug = '<affected-slug>';

2. Harden the component. Fall back to a placeholder when the image fails to load, so no user ever sees a broken icon:

<!-- product-card.component.html -->
<img
  [src]="product.image_url"
  [alt]="product.name"
  loading="lazy"
  (error)="onImageError($event)" />
// product-card.component.ts
onImageError(event: Event) {
  const img = event.target as HTMLImageElement;
  if (img.src.endsWith('/placeholder.svg')) return;   // avoid infinite loop
  img.src = '/assets/placeholder.svg';
}
Why This Works
  • Migrations are additive. A new migration patches the URL and preserves history — editing an old file breaks reproducibility for anyone who has already run it.
  • An onerror fallback means one bad URL never ships a broken card — a small placeholder tells the user the product exists, just without a photo yet.
  • Verify in DevTools' Network tab after the fix — no 404s for product images.
Related Pitfalls
  • Don't hotlink to third-party CDNs (Pexels, Unsplash) without a caching layer — they can rotate or remove images at any time.
  • Consider a build-time or test-time crawl over all image_urls to catch dead links before they ship.

8. Cart drawer locks the store

← back to bug
Root Cause

When the drawer closes, its visible panel animates off-screen — but the full-viewport backdrop element (or a duplicate of the panel from a re-open) is never removed from the DOM. The leftover element sits invisibly on top of the page with pointer-events: auto, catching every click.

Two failure modes tend to compound:

  • Missing cleanup on close — the close() method sets a visibility flag but doesn't remove the backdrop node or reset its pointer-events.
  • Race between close methods — the close button and the outside-click / Escape handlers each trigger their own close, and closing while a close animation is already running leaves the backdrop in a "closing" state that never finishes.
The Fix

Guard against re-entrant closes, and always tear down the overlay in a finally block so it happens regardless of animation state:

// cart-modal.service.ts
export class CartModalService {
  isOpen = signal(false);
  private closing = false;

  open() {
    if (this.closing) return;   // don't fight an in-flight close
    this.isOpen.set(true);
  }

  async close() {
    if (!this.isOpen() || this.closing) return;   // re-entrancy guard
    this.closing = true;
    try {
      await this.playCloseAnimation();
      this.isOpen.set(false);
    } finally {
      this.closing = false;                          // ALWAYS reset
    }
    this.isOpen.set(false);
  }
}
<!-- cart-modal.component.html -->
@if (isOpen()) {
  <div class="cart-backdrop"
       (click)="close()"
       [attr.aria-hidden]="!isOpen()"></div>
       ></div>
  <aside class="cart-drawer"
         role="dialog"
         (keydown.escape)="close()">
    <!-- … -->
  </aside>
}
/* cart-modal.component.scss */
.cart-backdrop {
  position: fixed; inset: 0;
  background: rgba(0, 0, 0, 0.4);
  /* animates out, but never removed from DOM */
  opacity: 0;
  transition: opacity 0.3s;
  /* When the @if evaluates to false, the element is removed entirely.
     If you must animate out first, use Angular's :leave animation trigger
     and DON'T also toggle a "closed" class that hides but keeps the node. */
}

.cart-backdrop[aria-hidden="true"] { pointer-events: none; }   /* belt and suspenders */
Why This Works
  • Angular's @if removes the node from the DOM when the condition is false — no leftover element, no leftover pointer events. Toggling a "hidden" CSS class instead is the classic trap: the node is still there and still catches clicks unless you explicitly set pointer-events: none.
  • The re-entrancy guard means a second close() call (from Escape landing while the button's close is already running) short-circuits instead of leaving a half-closed state.
  • The finally block guarantees the closing flag is reset even if the animation promise rejects — otherwise the drawer would be stuck in the closing state and never reopen.
  • pointer-events: none as a safety net means even if a stale backdrop somehow survives, it doesn't block clicks.
Related Pitfalls
  • Watch out for duplicate drawers from calling open() twice before the previous close finishes. The open guard above handles it; alternatively use a single global overlay slot.
  • If you use Angular's @if with an animation, use the :leave trigger so the element stays mounted only for the duration of the animation, then unmounts. Don't reimplement this by hand.
  • Test with keyboard-only navigation. If focus is trapped inside a "closed" drawer, that's another sign the element wasn't fully removed.
  • In DevTools, running document.elementFromPoint(x, y) in the console over a "locked" area will tell you exactly which invisible element is catching the click.

9. Stale header-search results

← back to bug
Root Cause

Each keystroke fires a new search request, but responses are applied in the order they arrive — not the order they were requested. On a slow network, the response for mon can land after the response for monstera, overwriting the correct results.

The Fix

Use a request-id (sequence number) and discard any response that isn't for the latest request. Even better in RxJS: switchMap, which cancels the previous in-flight request automatically.

// header.component.ts — plain-async version
private requestSeq = 0;

async onSearch(query: string) {
  const seq = ++this.requestSeq;
  const results = await this.searchService.suggest(query);
  if (seq !== this.requestSeq) return;   // a newer request has been issued
  this.suggestions.set(results);
}
// or, the RxJS way — switchMap cancels the previous request
this.query$
  .pipe(
    debounceTime(150),           // don't hammer the network
    distinctUntilChanged(),      // ignore no-op keystrokes
    switchMap(q => this.searchService.suggest(q))
  )
  .subscribe(results => this.suggestions.set(results));
Why This Works
  • The sequence guard is the simplest correct pattern — increment on request, compare on response, drop stale results.
  • switchMap is the declarative version — it unsubscribes from the previous inner observable when a new one arrives, so stale requests are cancelled at the network layer too.
  • Debounce + distinctUntilChanged reduces the number of requests to begin with — fewer races, less server load.
Related Pitfalls
  • Don't debounce so long that suggestions feel laggy — 100–200ms is the sweet spot for search-as-you-type.
  • Also handle the empty-query case: clear suggestions immediately rather than firing a network request for "".
  • If you need infinite-scroll or paginated results, switch to concatMap or exhaustMap — switchMap's cancellation would drop the wrong requests.
